# 小公館人文旅舍 新官網 + 直訂系統 + 員工後台 — 設計文件

日期：2026-11-24　狀態：定稿，待業主核准

## 1. 目的與緣由

小公館人文旅舍（NK Hostel，台北松山區南京東路五段 399 號 5 樓）的舊官網 https://www.nkhostel.com/main.php 是靜態 PHP 網站，沒有後台。「立即訂房」連到 SiteMinder 的訂房引擎（`app-apac.thebookingbutton.com/properties/nkhosteldirect`）。房價、折扣和庫存在 SiteMinder 後台調整，SiteMinder 再同步到 Agoda、Booking.com 等訂房網，以及館內的靈知 PMS。

老闆想要**一套自己的訂房系統**，理由是：
- 品牌官網和訂房體驗要達到國際前百大飯店的水準，訂房流程不要跳出官網。
- 線上刷卡直接進飯店的永豐銀行帳戶。
- 訂單、住客資料和報表留在自己手上。
- **會展店**，所以系統要能管理多館。宜蘭正在籌備的露營區未來可能也要納入。

## 2. 目標、非目標、反目標

**目標（第一階段）**
- 品牌官網，四種語言：繁中、英文、日文、韓文。
- 官網直訂：查詢可訂房型、選方案和加購、線上刷卡（永豐）、寄確認信、自助查詢和取消訂單。
- 串接 SiteMinder：從 SiteMinder 取得房價和庫存；直訂訂單、修改、取消回推到 SiteMinder。
- 員工後台：訂單、住客、內容管理、折扣碼、報表、帳號權限、操作紀錄。
- 資料結構支援多館，並能升級成「自主 PMS／房價庫存主控」（第二階段）。

**非目標（第一階段不做）**
- 自行管理房價和庫存（主控權仍在 SiteMinder）。
- 取代靈知 PMS：入住、退房、排房、房務仍在靈知處理。
- 直接串接 Booking.com、Agoda 的 API（繼續透過 SiteMinder）。
- 會員、點數制度：資料表預留，但不做介面。
- 露營區的任何功能：只在資料模型上確保放得進去。

**反目標（就算功能都能動，出現這些也算失敗）**
- **超賣**：直訂訂單沒進 SiteMinder，或庫存顯示過時。
- 存下卡號或 CVV，任何形式都不行（違反 PCI-DSS）。
- 金額不一致：訂單、刷卡、退款、報表的數字對不上。
- 看起來像模板站，沒有精品飯店的質感。
- 讓員工多一套要手動同步的系統。

## 3. 限制

- **房價和庫存的唯一真實來源是 SiteMinder。** 我們的系統只做快取，可訂量必須即時或接近即時地向 SiteMinder 確認。
- SiteMinder 的串接要用飯店名義申請。走 **SiteConnect**（給訂房引擎、通路的介面）需要通過 SiteMinder 審核和認證測試，時程不在我們掌控內。開發期間先用模擬器（mock）。
- 刷卡用**永豐銀行網路收單**，必須支援 3D 驗證。卡號由永豐的頁面或 token 機制處理，不進我們的伺服器。永豐 API 的實際規格（是否支援 token 化保存、預授權、部分退款）要拿到永豐的技術文件後確認，見第 9 節。
- 櫃檯繼續用永豐刷卡機（EDC）。第一階段的做法是後台手動登錄刷卡機收款，不直接連刷卡機。
- 個資依台灣《個人資料保護法》處理；歐美旅客的部分盡量對齊 GDPR 的精神（同意、刪除請求）。

## 4. 考慮過的做法

| 做法 | 內容 | 取捨 |
|---|---|---|
| **A（採用）SiteMinder 主控，我們做直訂通路** | 自建官網、訂房流程、金流、後台；房價庫存從 SiteMinder 同步；訂單回推 | 不會超賣、靈知不用動、上線最快；改價仍在 SiteMinder 後台 |
| B 我們當主控（自主 PMS） | 改價、庫存、排房都在自家後台；SiteMinder 只分發到 OTA | 最完整的自主權；但等於取代靈知，工程量大好幾倍，還要通過 PMS 介接認證 |
| C 連 SiteMinder 也取代 | 直接串 Booking、Agoda API | 要個別申請連線夥伴資格，維運負擔重，現階段不划算 |

老闆選 **A**，但**資料結構照 B 的標準設計**，之後升級 B 時不用重寫。

另外還有一個「包裝 SiteMinder 現成訂房引擎」的做法。這做法最快，但不符合「自己的系統」這個目標，所以排除。

## 5. 已決定的部分

### 5.1 技術（業主選定 Cloudflare）
- **平台：全部使用 Cloudflare**。選它是因為免費方案允許商業用途、不會因閒置而暫停、D1 內建時間回溯備份、R2 沒有流量費。比較過 Supabase + Vercel：要正式營運每月約需 US$45（Vercel Hobby 方案禁止商業用途，Supabase 免費版沒有備份）。
  - 網站和 API：Next.js（App Router）+ TypeScript + Tailwind，透過 OpenNext 部署到 Cloudflare Workers。
  - 資料庫：D1（SQLite），用 Drizzle ORM 管理 schema 和 migration。照片和檔案放 R2，並經過 Cloudflare Images 或圖片轉換服務處理。
  - 背景工作：SiteMinder 重送、對帳、入住前提醒用 Cron Triggers 和 Queues。
  - 員工後台登入：**Cloudflare Access**（50 人以內免費，可用 Google 帳號或 Email OTP 登入、支援 2FA、有登入紀錄）。系統內的角色權限另外由 `staff` / `roles` 表控制。
  - 寄信：Resend + React Email（或 Cloudflare Email Service）。
  - 開工前要再核對一次 Cloudflare 免費額度的最新公告。
- **向 `rentalflow-saas` skill 借用規則和模式，不照搬程式碼**：半開區間日期、單一重算入口的金額規則、先部署後 migration 也不會壞、多語 Email、CSS 變數做品牌主題、後台分頁、可訂狀態不快取過時。D1 沒有 RLS，所以存取控制要在 API 層統一實作。
- **不沿用**：完整卡號、CVV 的加密儲存。

### 5.2 多館資料模型（第一天就照 B 的標準）
- `properties`：館別，有類型（`hotel`／`campsite`），還有時區、幣別、地址、各語言名稱、SiteMinder property code。
- `unit_types`：房型或營位類型，記錄可住人數、床型、面積、設施、多語內容、照片，以及對應的 SiteMinder room type code。
- `units`：實體房間或床位、營位。第一階段只做資料，排房仍在靈知。
- `rate_plans`：價格方案（例如含早、不可退、連住優惠），含取消規則和對應的 SiteMinder rate plan code。
- `inventory_daily` / `rates_daily`：每日庫存、房價和限制（最短住宿天數、到店和離店限制）。**第一階段這些資料是 SiteMinder 的快取**（每筆標記來源和同步時間）；第二階段改成由我們主控。
- `reservations` + `reservation_rooms`：一張訂單可以有多間房，記錄來源通路、狀態歷程、SiteMinder 的確認號。
- `guests`：住客。`payments`：收款、退款、預授權，記錄方式（線上永豐／櫃檯刷卡機／現金／匯款）和永豐交易序號，**不存卡號**。
- `addons`（加購：早餐、接送、延遲退房等）、`promo_codes`、`content_pages`、`news`、`faqs`、`reviews`。
- `staff`、`roles`、`audit_log`。
- 預留：`members`、`loyalty`。
- 日期一律用半開區間 `[check_in, check_out)`，金額用整數（新台幣元），所有金額由同一個函式重算。

### 5.3 SiteMinder 串接
- 走 SiteConnect：接收房價、庫存、限制（ARI）的推送，或定期拉取；送出新訂單、修改、取消；處理確認回覆和重送。
- **在付款前**再即時確認一次可訂量。如果 SiteMinder 回推失敗，訂單標成「待同步」，在後台顯示紅色警示，並通知值班人員；背景會自動重試。
- 有對帳頁面：比對我們和 SiteMinder 兩邊的直訂訂單。

### 5.4 金流（永豐）
- 線上：使用永豐網路收單，經過 3D 驗證，依房價方案做全額付款或訂金付款。退款從後台發動，部分退款依永豐 API 的能力決定。
- 櫃檯：後台可以登錄「刷卡機收款」，記錄授權碼、末四碼、金額，用來對帳。
- 付款結果用永豐的伺服器回呼（server-to-server）為準，不以使用者瀏覽器跳轉回來的結果為準。

### 5.5 官網（前百大飯店規格）
- 頁面：首頁、房型列表和房型詳情、設施、團體和長租洽詢表單、評價、交通、周邊景點、最新消息、常見問題、隱私權和訂房條款。
- 每頁固定有訂房列（日期、人數）；房型頁能直接看到價格並訂房。
- 支援四種語言（next-intl），使用 hreflang，每種語言的網址各自獨立。
- SEO：在 schema.org 標記 Hotel 和 HotelRoom。目標 Core Web Vitals 達到「良好」，圖片用 AVIF 或 WebP，搭配 CDN。
- 無障礙：WCAG 2.1 AA。
- 文案、房型、照片從舊站移轉。視覺設計另外在設計階段提案，給業主選。

### 5.6 員工後台
- 角色：老闆（全部權限）、經理、櫃檯、行銷（只能管內容），權限可以依館別限制。
- 功能：
  - 營運總覽：今日入住和退房、未付款、待同步。
  - 訂單：查詢、修改、取消、退款、補收款、備註。
  - 住客。
  - 內容管理：四種語言的房型、照片、消息、FAQ、頁面。
  - 加購項目、折扣碼。
  - 報表：營收、通路、間夜數、取消率，可匯出 Excel。
  - SiteMinder 同步狀態和對帳。
  - 員工帳號。
  - 操作紀錄。
- 登入透過 Cloudflare Access，老闆和經理必須開啟兩步驟驗證（2FA）。

### 5.7 通知
- 寄給旅客：訂房確認、修改、取消、退款、入住前提醒，用旅客下單時的語言寄出。
- 寄給館方：新訂單、同步失敗、付款失敗。

### 5.8 業主已決定的營運規則
- **電子發票**：由靈知開立（維持現狀）。新系統不開發票；預付金額、加購項目和直訂方案都要隨訂單回推到 SiteMinder，再進入靈知，讓櫃檯在靈知裡看得到。
- **直訂價格**：在 SiteMinder 開「官網專屬方案」（直訂限定的 rate plan），房價從 SiteMinder 取得。折扣碼是我們系統內再疊加的優惠；回推的訂單金額以折扣後總額為準，並附上明細。
- **取消**：旅客在線上取消時，系統依房價方案的取消規則**自動退款**，不必員工審核。改日期一律請旅客聯繫館方，由員工在後台處理。

### 5.9 實作方的判斷（業主核閱時請確認）
- **付款前的可訂確認**：如果 SiteConnect 沒有即時查詢 API，就改用 SiteMinder 推送的 ARI 快取（每次推送就更新）。我們自己的訂單一成立，就先在本地扣庫存，回推成功後再以 SiteMinder 為準。這跟各家 OTA 承擔的風險相同，殘餘的超賣風險可以接受。
- **SiteMinder 認證前**：新官網可以先上線，「訂房」按鈕先連到現有的 SiteMinder 訂房引擎。認證通過後再切換成自家的直訂流程。
- **已扣款但訂單無法成立**（剛好售完，或回推一直失敗）：如果永豐支援預授權，就先授權，SiteMinder 確認後才請款；如果不支援，就自動全額退款，寄道歉信給旅客，並在後台警示、通知值班人員。訂單狀態要明確區分「已付款待確認」和「確認失敗已退款」。
- **多館**：第一階段只上線小公館一館，多館只做到資料模型的層次。金流和 SiteMinder 的設定綁在 `property` 上，每館可以有自己的永豐商店代號和 SiteMinder property。

## 6. 交給實作方決定的部分
- 程式架構、資料表欄位細節、API 設計、測試策略。
- SiteMinder 是用推送還是拉取同步，以及快取多久過期（前提是付款前一定即時確認）。
- 文案翻譯流程：機器翻譯後由人工校稿，或接翻譯平台。
- 部署環境（staging 和 production）和監控工具。

## 7. 分期
1. **第一階段**：第 5 節全部內容。SiteMinder 在拿到認證前先用 mock 開發。
2. **第二階段**：會員和回訪優惠；直接連櫃檯刷卡機。
3. **第三階段**：升級成 B，由自家後台主控房價、庫存、排房，評估是否取代靈知。
4. **之後**：宜蘭露營區以新的 `property`（類型 `campsite`）加入。

## 8. 業主要做的事
- 用飯店名義向 SiteMinder 申請 SiteConnect 開發者或通路資格，並提供 property code、房型代碼、價格方案代碼。
- 向永豐銀行申請網路收單特約和技術文件，以及測試環境的商店代號和金鑰。
- 提供或授權使用舊站的照片和文案；決定是否請攝影師重拍。
- 提供網域和 DNS 管理權限。

## 9. 待確認事項（拿到文件後由實作方確認）
- 永豐網路收單是否支援 token 化、預授權、部分退款、Apple Pay。
- SiteConnect 的訊息格式（OTA XML 版本）、ARI 推送的頻率，以及認證測試的項目。
